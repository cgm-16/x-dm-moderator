# Audit: is x-dm-moderator worth continuing? — 2026-09-17

Context: the client this v0.1 was specced for no longer needs it. Two questions —
is there a product here, and if so do we restart green or reuse?

## What was measured

| Instrument | Reading |
|---|---|
| `wc -l dmguard/*.py` | 5,602 source lines, 42 modules |
| `wc -l tests/*.py` | 9,920 test lines, 37 files |
| `uv run pytest -q` (macOS, env roots set) | 266 passed, 0 failed, 0 skipped, 5.9s |
| `uv run ruff check .` | clean |
| `git log \| wc -l`, last commit | 127 commits, last 2026-03-24 (~6 months idle) |
| `gh issue list --state open` | 20 open, none blocking the core pipeline |

The suite still passes cold after six months with `torch>=2.10` / `transformers>=5.3`
unpinned. The code is alive, not rotted.

## Question 1 — is there a product?

Three findings, in order of how much they move the answer.

### 1. The ingress premise changed in our favour (verified 2026-09-17)

The frozen spec assumed DM webhooks meant an enterprise relationship. X's current
pay-per-usage pricing bills `dm.received` webhook events at **$0.010 per event
delivered** and DM event reads at **$0.010 per resource**, with no flat-rate tier
gate — the $200 Basic and $5,000 Pro tiers closed to new signups 2026-02-06 and
pay-per-use is now the default.

`GET /2/dm_events` also lists events with `max_results` + `pagination_token` over a
30-day window, so **polling is a plausible ingress**. That is the single most
important finding in this audit: it would delete the entire reason the project
needs DuckDNS, Traefik, ACME TLS-ALPN-01, public 443 reachability, and a Windows
service manager per install.

What is verified: listing, pagination, 30-day retention. Deduplication needs no new
work — `jobs.event_id` is already `NOT NULL UNIQUE` with an FK to
`webhook_events(event_id)`, so a poller re-seeing an event is a no-op by schema.
I did **not** verify a `since_id` parameter on this endpoint; the docs page lists
only `max_results` and `pagination_token`. Do not plan around `since_id`.

### 2. The deployment model is not a product

Single Windows host + NVIDIA CUDA GPU + Servy-managed services + one X account per
machine + a public hostname per customer is a bespoke install. It was the right
shape for one client. It cannot be sold to a second customer without an engineer
on the call. Productizing means replacing the deployment story regardless of how
good the code is — which is exactly what finding 1 makes cheap.

### 3. The moderation logic is not the moat

The actual differentiated IP is `moderator.py` (256 lines) + `classifier_llavaguard.py`
(166 lines) ≈ 420 lines: LlavaGuard v1.2 0.5B, act on O2 only, 1fps frames from
t=1..12s, block if any frame unsafe. That is a weekend of work for a competent
engineer. The value is in the packaging and the trust, not the algorithm.

### The two open risks — neither is a code question

- **Substitution — checked 2026-09-17, and the client's complaint holds.** See
  "Does X already solve this?" below. Short version: X hides and warns; X never
  blocks. The gap is structural, not a model-quality gap X closes with a better
  classifier.
- **Unit economics.** ~$0.02–0.03 per moderated media DM in X API charges alone,
  before compute. Fine for a "someone is brigading me right now" tool sold to
  creators, journalists, and public figures. Fatal for a $5/mo consumer app.
  A user taking 1,000 DMs/day costs $20–30/day to moderate.
- **Idle polling cost — unpriced, and it can invert the recommendation.** The
  webhook path bills only on delivery. A poller bills on every request whether or
  not a DM arrived. At the current 5s interval that is ~17k requests/day/account.
  The pricing page quotes `$0.001 per owned resource read`; if an empty
  `dm_events` list bills at that rate, idle polling is ~$17/day/account and the
  "delete the edge layer" move is a cost regression, not a saving. **Whether an
  empty list read bills is not documented.** Measure it against a live credit
  balance before committing to polling.

### Does X already solve this? — read from help.x.com, 2026-09-17

The client said X could not filter gore properly. That claim needed checking, because
if X's own filters cover it the product has no reason to exist. Primary source:
`help.x.com/en/using-x/direct-messages` and `/direct-message-faqs`, read in-browser
(both pages are Cloudflare-blocked to `curl` and WebFetch).

What X actually ships, verbatim:

- **A graphic media filter, on by default.** "There will be a displayed warning over
  graphic media in DMs, for both people you follow and unknown senders. Additionally,
  if it's from someone you don't follow, we'll also treat it like spam and move it to
  the bottom of your Request inbox."
- **Media hidden in requests.** "All media will be hidden prior to accepting the
  message. If you wish to view the hidden media, click or tap View media."
- **A quality filter on the Requests tab**, which "hides conversation requests we
  think may be lower quality."

Four gaps, and they are the whole product:

1. **X hides. X never blocks.** The FAQ lists exactly three ways to stop a sender —
   Block, DM block, Report — and all three are manual, per-sender, after the fact.
   X will not act on the sender for you. That *is* the client's pain: not "I saw
   something awful", but "I spent an hour a day opening requests and clicking Block."
   No amount of improvement to X's filter touches it.
2. **Deleting a request does not stop the sender.** "Deleting a message will not
   prevent that account from sending you messages in the future." Triage without
   blocking is unbounded work — the same sender comes back tomorrow.
3. **Both filters are mobile-only.** The graphic media filter: "This feature is only
   available currently on iOS and Android devices." The quality filter: "by default,
   we filter lower-quality requests ... for the X for iOS and Android app." Anyone
   triaging DMs at a desk — which is everyone doing it as work, including an
   assistant or a comms team — gets neither.
4. **The verdict is opaque and unactionable.** A blur is not a category, a confidence,
   or an audit row. There is no way to say "block on O2 violence, never on nudity,"
   and no record of what was decided and why.

So the honest framing: X's filter is probably fine at *hiding*. It does not *decide*
and it does not *act*. The product is not a better filter — it is an **auto-triage
and auto-block agent**, and that is a category X has structural reasons never to
enter, since a false-positive block silently mutates the user's social graph.

This raises the product's floor and narrows its market at the same time. The buyers
are people who (a) take real DM volume, (b) cannot just close DMs, and (c) triage on
desktop or hand it to someone else. Creators with open DMs, journalists, public
figures, trust-and-safety teams. Not a general consumer audience.

**Verdict: conditionally yes, but it is a different product than the one that was
built.** Hosted multi-tenant, OAuth sign-in, polling ingress, cloud or API-hosted
classifier. Not a local Windows appliance. The condition is demand validation, not
engineering.

## Question 2 — green field or reuse?

**Reuse.** Ori's prior — "I'd have to scrap most of the working code" — is not what
the coupling grep shows. The client-specific rot is concentrated in the setup and
edge layer. The moderation pipeline is platform-neutral, typed, tested, and green.

| Bucket | Source LOC | Share | Modules |
|---|---|---|---|
| **Keep as-is** | 3,113 | 56% | `moderator` `worker` `scheduler` `job_machine` `schema` `db` `repo_*` (753) `pruner` `recovery` `x_client` `x_oauth` `x_dm` `media_dispatch` `media_download` `frame_extractor` `classifier_*` (420) `config` `logging_setup` `secrets` |
| **Rewrite** | 1,380 | 25% | `app` (646 — keep `/health`, `/version`, dispatch; drop webhook receiver), `cli` (734 — keep allowlist/blockstate/selftest, drop setup/service commands) |
| **Delete** | 1,109 | 20% | `setup_flow` (396) `setup_state` (171) `edge` (78) `service_manager` (119) `templates` (68) `paths` (92) `webhook_auth` (27) `x_webhooks` (93) `setup_logger` (65) + `dmguard/traefik/` |

Tests net out the same way: of 9,920 lines, ~6,284 (63%) survive; ~3,636 die with
the ingress layer (`test_cli` alone is 91 platform hits, `test_setup_flow` 40).

Green-field would mean rewriting a clean, green, 3,100-line async SQLite job queue
and moderation pipeline to arrive at the same thing. The honest counter-argument is
that the valuable part is only ~420 lines, so restarting is *cheap* — but cheap is
not free, and it buys nothing the delete list doesn't.

## What the reuse path actually is

1. **Validate demand first.** X's filtering is checked and does not cover it — that
   question is closed. What is still open is willingness to pay. Talk to five people
   who take this volume, and lead with "it blocks them for you," not "it filters."
2. **Gated on the idle-polling measurement above.** If empty polls are free or
   near-free: delete the edge layer, replace the webhook receiver with a
   `GET /2/dm_events` poller feeding the existing `jobs` table — the job queue,
   retry math, and state machine do not change. If empty polls bill per request:
   keep webhooks, and replace the per-customer DuckDNS/Traefik host with one
   shared hosted endpoint, which removes the same install burden a different way.
   Either branch kills `setup_flow`, `edge`, `service_manager`, and `templates`.
3. Drop the Windows path policy — `paths.py` exists only to serve
   `C:\Program Files\XDMModerator\`. Plain env vars / XDG.
4. Decide classifier hosting: keep LlavaGuard local (cheap, needs a GPU box) or
   call a hosted VLM (no GPU, higher per-unit cost). This is the one genuinely
   open architecture question.
5. Multi-tenant: `dmguard` is single-account throughout. Sender-state tables need
   an account dimension. This is the largest piece of *new* work.

Housekeeping, independent of the decision: 27 `.codex-memory-*.md` files sat in the
repo root, gitignored by design (`.gitignore:13`, "Agent Memories"). Deliberate local
scratch, not accidental clutter — but that also made them the single largest body of
project knowledge that would never have survived this machine. They have since been
triaged into `docs/journal/` (see the mothball commit). `specs.md` is explicitly a
frozen v0.1 reference and is now marked superseded by this document.

# Addendum — hosted SaaS model (decision, 2026-09-17)

Ori's call: a hosted multi-tenant service. Users sign in with X, the server holds
their tokens and does triage and blocking on their behalf. Not an installable
appliance.

This is the right shape and it resolves the open gate above. It also changes the
reuse arithmetic enough to restate it.

## The one thing that should scare us

**Block Party is the closest comparable and it is dead.** A funded startup doing
exactly this category — an anti-harassment layer over Twitter DMs and mentions —
went on hiatus in May 2023 when Twitter paywalled the API. Block Together shut down
in 2021. MegaBlock stopped working after the repricing.

None of these died from policy enforcement or lack of demand. They died because
**X unilaterally repriced the input their entire COGS depended on.** We are proposing
to build a business whose per-unit cost is set by a party with a documented history
of changing it without notice, and which closed the $200 and $5,000 tiers to new
signups as recently as 2026-02-06.

That is not a reason not to build it. It is a reason to keep the X-specific surface
deliberately thin — `x_client`, `x_dm`, `x_oauth`, `x_webhooks` is already that
boundary, ~550 lines — so a reprice means porting rather than dying. Treat "which
platform" as a runtime concern from day one, not a rewrite.

## What the SaaS model settles

**Webhooks win; polling is dead.** This reverses the gate in the main audit. Polling
costs per request whether or not a DM arrives, so at N tenants it is N × ~17k
requests/day of pure idle spend. Webhooks bill only on delivery ($0.010/event). One
hosted endpoint serves every tenant.

Consequence: `webhook_auth.py` (27) and `x_webhooks.py` (93) move from **delete** back
to **keep** — they become core infrastructure rather than per-customer install junk.
What dies is the *per-customer edge*: DuckDNS, Traefik, ACME, Servy, the Windows path
policy. That was always the actual rot.

**Unverified:** whether one registered webhook can carry N subscribed users under the
current pay-per-use Activity API. The old Account Activity model worked that way
(one webhook env, N subscriptions). Confirm before committing — if it is one webhook
per user, the ingress design changes again.

## Revised reuse arithmetic

| Bucket | LOC | Share |
|---|---|---|
| Keep | 2,631 | 46% |
| Rewrite | 1,982 | 35% |
| Delete | 989 | 18% |

Moved into **rewrite** by the hosting decision:

- `secrets.py` (85) — a single-account `FileSecretStore` becomes a store of N users'
  OAuth refresh tokens. That is a breach magnet, not a config file. Per-tenant
  envelope encryption, KMS-backed. This flips from asset to liability.
- `x_oauth.py` (256) — PKCE with a local browser popup is a desktop flow. SaaS needs
  a server-side redirect callback.
- `classifier_runner.py` (95) + `classifier_llavaguard.py` (166) — spawning a child
  process per job with a 180s timeout is fine for one account and ruinous at N.
  Needs a resident model server. The upside is real, though: LlavaGuard 0.5B is small
  enough that one GPU batches across all tenants. Shared inference is the best
  possible arrangement, where a GPU box per customer was the worst.

Still **keep**, but every one needs an `account_id` column and predicate — this is the
largest piece of genuinely new work: `schema.py` + all `repo_*` = **892 lines**,
`repo_senders.py` (308) most of all, since allow/block/block-failed state is keyed by
sender with no tenant dimension anywhere.

## Four things the hosting decision breaks that are not code

1. **Consent. OAuth sign-in is not enough.** X's Developer Policy: "you must get
   express and informed consent from people before doing any of the following: Taking
   *any* actions on their behalf," and explicitly, "a person authenticating into your
   service does not by itself constitute consent." Auto-blocking needs its own
   affirmative consent step, separate from the OAuth screen. This is a product
   requirement, not a checkbox we can bury.
2. **Fail-open is now wrong.** In v0.1 the client was also the operator, so a silent
   failure was visible to the person it affected. As a service, fail-open means
   customers believe they are covered while gore lands in their inbox. Failures have
   to degrade visibly.
3. **Wrong blocks are our liability now.** We are mutating someone's social graph from
   a server they do not control. `repo_audit.py` (94) already exists and earns its
   keep — but it needs an undo path, and probably a quarantine-instead-of-block mode
   for cautious customers. Note also that "never perform bulk, aggressive, or spammy
   actions" means a backfill sweep over historical DMs is out; block on live events
   only.
4. **COGS scales with abuse, which is adverse selection.** At ~$0.02–0.03 per
   moderated media DM, the customers who need this most cost the most to serve. Flat
   per-seat pricing loses money on exactly the users who prove the product. Price on
   usage, or cap it.

**One more structural change:** the worker is sequential by spec ("single sequential,
poll every 5s"). At N tenants, one customer's 12-frame video stalls everyone.
`worker.py` is only 119 lines so concurrency is cheap to add, but `scheduler.py`'s
claim query needs a per-tenant fairness dimension, not just `next_run_at ASC`.

# Addendum 2 — can one webhook carry N users? (verified 2026-09-17)

**Yes: 1,500 subscriptions on self-serve.** But only on the right API, and the spec
this repo was built to targets the wrong one.

## The API we specced is deprecated, and its ceiling was 3

`docs.x.com/x-api/account-activity/introduction` now opens with: "The Account Activity
API (AAA) is being deprecated. Check out the X Activity API (XAA) for real-time user
activity delivery going forward." Its Introduction and Quickstart are both marked
DEPRECATED in the nav.

AAA's own feature summary, verbatim:

| Tier | Number of Unique Subscriptions | Number of Webhooks |
|---|---|---|
| Pay Per Use | 3 | 1 |
| Enterprise | 5000+ | 5+ |

**Three.** Had we built the SaaS on AAA as `specs.md` describes, we would have hit a
hard wall at customer number four and the only way past it was the enterprise contract
we assumed had gone away.

## XAA is the go-forward API and it is better for us in four ways

From `docs.x.com/x-api/activity/introduction`:

**1. The ceiling is real.**

| Package Tier | Maximum Subscriptions |
|---|---|
| Self-serve | 1,500 |
| Enterprise | 75,000 |
| Partner | 150,000 |

1,500 customers before we have to talk to anyone at X.

**2. Subscriptions are per event type, not per user.** `POST /2/activity/subscriptions`
takes `{"event_type": "dm.received", "filter": {"user_id": "..."}}`. AAA was
all-or-nothing — "You will receive all related activities below for each user
subscription", meaning Posts, Likes, Follows, Blocks, Mutes, typing indicators, read
receipts, and "the returned Posts ... count towards the monthly Post cap." XAA lets us
subscribe to **only** `dm.received`. That is the difference between paying for every
like on a creator's account and paying only for inbound DMs. It is the single biggest
COGS lever in this whole design, and it reverses the adverse-selection worry in
Addendum 1 considerably — a high-engagement creator no longer costs more unless the
DMs themselves are high-volume.

**3. OAuth 2.0, not OAuth 1.0a.** `dm.received` is a "private event": these "require
user-context (OAuth 2.0) authentication" and "Subscriptions for private events can only
be created for users who have authorized your application." AAA required OAuth 1.0a
3-legged. Our existing `x_oauth.py` PKCE flow is the right family — it still needs the
server-callback rewrite, but not an auth-scheme change. X's own wording here also lines
up with the Developer Policy consent requirement: "The user must explicitly grant
permission for your app to access these events."

**4. There is a third ingress option we did not know about.** `GET /2/activity/stream`
— a persistent HTTP stream. We dial out; no public HTTPS endpoint, no CRC, no inbound
TLS, no "URL cannot include a port" constraint. For a hosted service this may be
simpler than webhooks. Worth a serious look before committing to the webhook path.

## What this means for the code

`x_webhooks.py` (93) is already on the right API — it calls `POST /2/webhooks`,
`GET /2/webhooks`, `PUT /2/webhooks/:id`, which is exactly the current V2 Webhooks API,
not the deprecated AAA webhook endpoints. `webhook_auth.py` (27) does HMAC-SHA256 with
the `sha256=` prefix, matching the documented `x-twitter-webhooks-signature` scheme.
Both keep, unchanged.

What is missing entirely is the subscription half — `POST /2/activity/subscriptions`
and its lifecycle (create on signup, delete on churn, handle revokes). No equivalent
exists in the codebase. That is new work, but small: one module against five endpoints.

## The risk that matters more than pricing

XAA files `dm.received` under "**Legacy** DM events", described as "the legacy,
unencrypted DM system". Alongside it sits a parallel encrypted set — `chat.received`,
`chat.sent`, `chat.conversation_join`.

X is moving DMs to encrypted chat, and X has labelled the system this entire product
depends on as legacy. **If DMs go end-to-end encrypted by default, server-side media
classification becomes impossible** — we cannot classify what we cannot decrypt, and a
hosted service is precisely the architecture that cannot follow the data into a client.

That is a larger existential risk than repricing, and it argues for a specific hedge:
keep the classifier callable from a client-side context, and do not let the server
become the only place moderation can physically happen. Worth understanding the XChat
migration timeline before committing to a hosted-only architecture.
